# LOA Vehicle Reservation & Trip Ticket

Vehicle reservation and trip-ticket system for the Lyceum of Alabang Physical Facilities
Management Office. Requisitioners file requests; the Head of Transport Services reviews first,
followed by the Director for Administration and the President.

During the Head of Transport Services review, vehicle details and the assigned driver's name are
recorded. They are shown on the trip ticket.

Every finally approved ticket remains searchable in its saved request record. Administrators can
use **Trip Archive & Analytics** to search by ticket, destination, requester, driver or vehicle;
filter by travel dates; and review ticket totals, completed trips, daily activity and destination
counts. Trip analytics count completed requests as actual trips; approved or dispatched tickets
remain in the archive but are not counted as completed journeys.

All data is stored in MySQL (Laragon locally). There is no demo request data: setup seeds
one administrator account and the document header. The administrator creates and assigns the
Head of Transport Services, Director for Administration and President accounts after setup. Admins
maintain the LOA phone directory; signed-in users can view assigned contacts there.

## Requirements

- Node.js 20+ and npm
- Laragon with MySQL or MariaDB running

## Local setup (Laragon)

```sh
npm install
npm run db:setup   # creates the database, a limited app user, and all tables
npm run db:seed    # creates the initial administrator and document header
npm run dev
```

`db:setup` connects as MySQL root (Laragon default: user `root`, empty password). If your
root account has a password, set `MYSQL_ROOT_USER` / `MYSQL_ROOT_PASSWORD` for that one
command. It generates a random password for the application user, writes everything to
`.env` (gitignored) and never prints it. The app user is granted only
`SELECT, INSERT, UPDATE, DELETE` on the `loa_vrtt` database.

`db:seed` prints an initial password once for the administrator account. The administrator
must choose a new password at first sign-in, then create and assign the Head of Transport Services,
Director for Administration and President accounts from Profile. Each new signatory account gets a
generated temporary password emailed to its configured institutional address and must change it at
first sign-in. The seeded
administrator account:

| Role          | Email              |
| ------------- | ------------------ |
| Administrator | `admin@loa.edu.ph` |

`db:seed` does not delete existing accounts in an already initialized database. To preserve
request and signature history, the administrator should create new signatory accounts and replace
the current stage assignments; unassigned legacy accounts cannot approve or return requests.

Requisitioners can create accounts at `/register` only with a Lyceum Google Workspace/Gmail
address ending in `@lyceumalabang.edu.ph`. The app sends a six-digit OTP to that institutional
address and creates the account only after the code is verified. Personal `@gmail.com` and other
domains cannot self-register.
Approver, administrator, and assistant accounts cannot be self-registered. The administrator
can create named assistant accounts and assign them as alternate signatories from Profile.
Assistant accounts use a separate Assistant role and do not receive Transport Personnel access.
Administrators can issue a one-time temporary password for any non-administrator account from
Profile; the user is signed out of active sessions and must choose a new password at next sign-in.

## Environment

Copy values from `.env.example` when setting up a new environment. Never commit `.env`.

| Variable                                                                                  | Purpose                                                                                   |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `DB_HOST` … `DB_PASSWORD`                                                                 | MySQL connection for the limited application user                                         |
| `TICKET_VERIFICATION_SECRET`                                                              | Private signing key for official ticket QR verification; generated by `db:setup`          |
| `SITE_URL`                                                                                | Public origin used for canonical links, Open Graph, sitemap                               |
| `ALLOWED_EMAIL_DOMAINS`                                                                   | Institutional domains accepted for admin-created accounts                                 |
| `GA_MEASUREMENT_ID`                                                                       | Optional GA4 ID, loaded only after analytics consent                                      |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`, `GOOGLE_SENDER_EMAIL` | Gmail sender credentials; the approved personal sender is `markjosephturingan4@gmail.com` |

To connect the sender locally, configure the Google OAuth client ID and secret, add
`http://localhost:8080/api/gmail/callback` as an authorized redirect URI, start the app, and visit
`/api/gmail/connect`. Set `GOOGLE_SENDER_EMAIL=markjosephturingan4@gmail.com` and authorize that
personal Gmail account. The callback rejects a different Google account and saves only the
refresh token; the configured sender address is not changed. It does not send a test email.
If the sender was connected before email identity verification was added, reconnect it so Google
grants the email identity scope as well as Gmail send permission. Restart the dev server after
connecting. Run `npm run db:setup` to create the registration OTP table before enabling
registration email.

The personal Gmail account is the sender only; it is not used as a request or ticket recipient.
Workflow messages go to the configured signatory/alternate account that owns the next action.
Official trip tickets go to the requisitioner who owns the request. New signatory account details
and password resets go to the email address configured for that account.
The request or account change is committed before Gmail delivery, so a mail failure is reported
to the administrator and does not undo the saved action. Final-approval messages to requisitioners
are sent when staff send the official ticket; that message includes the ticket image and the
requisitioner's configured account address is used as the recipient. Each in-app notification shows
whether its email was sent, failed, or is still pending; older notifications have no delivery status.
Ticket delivery can be retried from the print page. Requests changed before email delivery was
enabled are not emailed retroactively. Production must use server-side OAuth secrets and a public
HTTPS `SITE_URL`; never expose OAuth credentials or refresh tokens with a `VITE_` prefix. Google's
OAuth policies, sender restrictions, and recipient mail systems can still reject delivery.

## Security notes

- Sessions are random 256-bit tokens stored hashed in MySQL and sent in an httpOnly,
  SameSite=Lax cookie; the cookie is `Secure` when `SITE_URL` is HTTPS.
- Passwords use scrypt with a per-user salt. Five failed sign-ins lock the account for
  15 minutes. Sign-in responses do not reveal whether an email exists.
- Every server function re-checks the session and role server-side. Requisitioners can
  only read their own requests and notifications; there are no client-only checks.
- Official trip tickets include a QR verification link. The public verification page checks a
  server-signed ticket reference against the approved request and sent ticket in MySQL, then shows
  the authoritative request date, travel dates, and destinations for comparison. The signing key
  must remain private and consistent across application instances.
- All SQL uses prepared statements. Inputs are validated with Zod on the server.
- Security headers (CSP, HSTS, X-Frame-Options, nosniff, Referrer-Policy,
  Permissions-Policy) are set in `src/server.ts`. Production error pages hide stack traces.
- Analytics are first-party and cookie-free by default (path counts only, no IP, user or
  query string). GA4 is optional and never loads before consent.

  Registration verification emails use the standard branded OTP template in
  `src/lib/email-template.ts`. OTPs expire after 10 minutes, can be resent once per minute, and
  allow at most five verification attempts. The Gmail connection endpoint is available only on
  localhost in non-production; message delivery uses the server-only Gmail API sender.
