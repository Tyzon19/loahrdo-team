# Security model

## Authentication

- Main accounts use salted scrypt password hashes.
- Password recovery uses time-limited verification codes.
- Registration uses institutional email OTP validation.
- Google OAuth supports institutional internal accounts and a separate external COE client.
- Main, HRDO, and Permission Slip modules use separate session tables.
- Account lockout and forced password changes are implemented.

## Authorization

Authorization is role-based and is enforced inside server functions. `src/lib/access.ts` and module-specific access helpers distinguish:

- Requisitioners.
- Transport stages.
- HRDO staff and administrators.
- Permission Slip signatories and administrators.
- Super administrators.
- Assistants and operational roles.

The central administrator role does not automatically grant approval authority. The Permission Slip designated director role can approve, but module administrators have controlled read or management access.

## Session protection

Session identifiers are stored as SHA-256 token hashes in database session tables. Sessions use an expiry timestamp and are tied to user-agent information. Logout invalidates module sessions.

## Data protection

- Zod and custom schemas validate input lengths and formats.
- HTML email and user-controlled text must be escaped in generated messages.
- Public verification is limited to approved ticket tokens.
- Uploaded COE and receipt data are restricted to authorized retrieval.
- Database credentials and OAuth secrets are environment variables.
- `.env` and environment-specific secret files must not be committed.

## Audit trail

Request history, COE history, Permission Slip history, system access history, synchronization logs, and notification records provide operational traceability.

# Technical requirements

| Requirement | Recommended value |
| --- | --- |
| Node.js | 20 or newer |
| Package manager | npm |
| Database | MySQL or MariaDB |
| Browser | Current Chrome, Edge, Firefox, or Safari |
| Device | Desktop, tablet, or mobile with responsive layout |
| Network | HTTPS in production |

# Environment categories

The implementation uses database, public-origin, OAuth, Gmail, ticket-signing, analytics, and attendance synchronization variables.

## Required application values

- `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`.
- `DB_CONNECTION_LIMIT` and database pool limits.
- `SITE_URL`.
- `TICKET_VERIFICATION_SECRET`.
- `ALLOWED_EMAIL_DOMAINS`.

## Google and Gmail values

- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`.
- `GOOGLE_EXTERNAL_CLIENT_ID` and `GOOGLE_EXTERNAL_CLIENT_SECRET`.
- `GOOGLE_SIGNIN_REDIRECT_URI`.
- `GOOGLE_REDIRECT_URI`.
- `GOOGLE_SENDER_EMAIL`.
- `GOOGLE_REFRESH_TOKEN`.

## Attendance values

- `GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON`.
- `LATE_ABSENCES_WEBHOOK_SECRET`.
- `LATE_ABSENCES_NON_TEACHING_SPREADSHEET_ID`.
- `LATE_ABSENCES_COLLEGE_SPREADSHEET_ID`.
- `LATE_ABSENCES_BASIC_ED_SPREADSHEET_ID`.

Secrets must be provided through server environment configuration. Public browser environment variables must never contain database or OAuth secrets.
