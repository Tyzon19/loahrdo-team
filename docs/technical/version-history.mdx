## How to record future versions

When a new release is deployed, add a new `<Update>` block at the top of this page with the following:

1. **Label:** Use the release date in `YYYY-MM-DD` format.
2. **Description:** Use a short version tag (for example, "v1.1", "v1.2", "v2.0").
3. **Body:** List the changes in plain language. Include any of the following that apply:
   - New features or modules
   - API or route changes
   - Database schema changes
   - Role or permission changes
   - Security updates
   - Dependency upgrades
   - Documentation corrections or additions
   - Bug fixes with affected areas

Keep the list concise and verifiable. Link to related technical pages when a change affects architecture, modules, database, or API.

Example format for the next entry:

```mdx
<Update label="2026-12-01" description="v1.1">
  - Added new report export feature to the trip archive
  - Updated `DB_CONNECTION_LIMIT` default from 5 to 10
  - Fixed attendance sync webhook timeout for large spreadsheets
  - Documentation: added environment variable reference for new `REPORT_EXPORT_SECRET`
</Update>
```

If a release contains breaking changes, prefix the description with "BREAKING" and add a `<Warning>` inside the update body explaining what administrators must do before upgrading.
